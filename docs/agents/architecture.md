# Architecture — OpenPhonograms

How the codebase is organized, why it's shaped this way, and where to
make changes safely. Read this before adding a new generator, refactoring
the renderer, or onboarding.

> **Status:** Living document. Updated after every major refactor. See
> [AGENTS.md](../../AGENTS.md) for the 30-line project overview.

## Module Boundaries

### `framework/` — library code

Pure-Python, importable from any script. **No side effects on import.**
No `if __name__ == "__main__"` here.

- `phonograms.py` — owns SINGLE, MULTI, MULTI3, MULTI4, PG_STAGE. The
  canonical catalog of all 72 phonograms. Other modules import from here.
  Adding a new PG? Edit this file, run `just check-coverage` to confirm
  the catalog matches `lesson-catalog.csv`.

- `render.py` — Markdown→PDF pipeline. Public surface:
  - `render_md_to_pdf(md_path, pdf_path, doc_type)` — render one file
  - `_stage_from_path(md_path)` — detect stage from path
  - `resolve_image_path(src, md_file)` — image src resolution
  - `md_to_html(md_text, md_file)` — markdown→HTML (used by `render-extras.py`)
  - `PAGE_CSS` — Atkinson Hyperlegible + WCAG palette. Modify with care;
    all 887 rendered PDFs will pick up the change.

- `lesson-catalog.csv` — 248 rows. Authoritative source for stage, type,
  phonogram, rule, and reader mapping. Parsed by every check-*.py script.

- `fonts/` — 4 TTF files. Required for `@font-face` in `render.py`.
  Atkinson Hyperlegible is SIL OFL 1.1 (see `framework/fonts/OFL.txt`).

### `scripts/` — CLI entry points

Each script has `def main():` and an `if __name__ == "__main__"` guard.
Scripts are *consumers* of `framework/`, never the other way around.

Two categories:
- **Generators** (`generate-*.py`): emit MD files into content directories.
  Always idempotent — running twice produces the same output.
- **Builders** (`build-*.py`): compose PDFs into larger artifacts
  (packs, release ZIPs, merged stage PDFs).
- **Checkers** (`check-*.py`): read-only validators. Exit 0 = pass,
  exit 1 = problem found. Used by `just check` and `just pre-commit`.
- **Renderers** (`render-*.py`): walk source MD files and produce PDFs.

### `tests/` — pytest discovery

- Fast suite (90 tests, 1.5s): importable structure checks, decodability,
  render, catalog consistency. Run via `just test`.
- Slow suite (29 tests, 65s): invoke real CLI scripts, verify ZIP
  contents, render PDFs. Marked `slow`. Run via `just test-slow`.

## Shared Data Sources (issue #14)

The phonogram catalog was the worst duplication offender: `SINGLE`, `MULTI`,
`MULTI3` dicts lived in `scripts/generate-worksheets.py` and the stage
mapping was duplicated in `scripts/generate-stage3.py`. **After the #14
refactor, both live in `framework/phonograms.py`.** Other modules import
from there.

If you need to:
- **Add a new phonogram** → edit `framework/phonograms.py`, run
  `just check-coverage` to verify the catalog matches `lesson-catalog.csv`.
- **Update word lists** → edit `framework/phonograms.py`. The game
  (`games/phonogram-trainer.html`) and all worksheets read from here.

## Design Decisions

### Why we don't use Jinja2 (yet)

The `framework/requirements.txt` lists `jinja2`, and the issue #14 spec
mentions migrating ad-hoc `str.format()` templates to Jinja. We chose
**not to migrate** for these reasons:

1. **Format strings are simple.** Most templates are 5-20 lines with
   1-3 substitutions. Jinja adds a parser dependency for no real win.
2. **Tests already cover template output** via the worksheet catalog
   checks. Regressions surface fast.
3. **Content authors edit MD directly** (not Python templates), so
   Jinja's "designer-friendly" benefit doesn't apply here.

If we ever build a content-management UI, Jinja becomes valuable. Until
then, `str.format()` is the right tool.

### Why we don't split `render.py` into a package

`render.py` is 430 lines. Tempting to split into `render/markdown.py`,
`render/pdf.py`, `render/images.py`. We kept it monolithic because:

1. **119 tests guard the public API.** Splitting would require a
   refactor + test rewrite for zero behavior change.
2. **Cross-module state is tight** (PAGE_CSS, PROJECT_ROOT, OUT paths).
   A package would force `from .markdown import convert; from .css import PAGE_CSS`,
   adding import noise without hiding complexity.
3. **The single file is grep-friendly** when debugging a rendering issue.

When `render.py` crosses ~800 lines, revisit. For now, one deep module.

### Why we mirror content to `stage-N/` subdirs

The release ZIP organizes content by stage (per issue #25). Source MDs
stay flat because:
- Existing scripts (`build-lesson-pack.py`, `check-*.py`) reference flat paths.
- Editors work better with shallow directories.
- The `stage-N/` mirrors are *outputs* of the generator, not *inputs*.

If a future refactor changes this, update the test suite first — the
`test_decodability.py` and `test_render.py` tests rely on flat paths.

## Anti-Patterns to Avoid

1. **Importing from `scripts/` into `framework/`.** This creates a
   circular dependency — `framework/` is the foundation, `scripts/`
   build on it. If `framework/phonograms.py` needed stage mapping from
   `scripts/`, the foundation would be built on top of the house.

2. **Defining the same data in two places.** If you find yourself
   copying the `SINGLE` dict, add an import to `framework/phonograms.py`
   instead.

3. **Hand-editing generated content.** The lesson readers, worksheets,
   and reader animals are all generated. If you need to change a story,
   fix `scripts/generate-readers.py` or `scripts/generate-animal-readers.py`,
   not the MD output. (Exception: `lessons/stage-1/pa-*` and
   `lessons/stage-2/reader-1.md` are hand-edited — see AGENTS.md.)

4. **Adding a new PDF without updating `build-release.py`.** Every PDF
   in `build/` should be reachable by some `--no-*` flag in
   `build-release.py`. If it isn't, the release ZIP is incomplete.

## When You Need Help

- Run `just doctor` to verify your environment matches CI.
- Run `just check` to catch drift, overflow, coverage, image issues.
- Run `just test` to verify your changes don't break the 119-test suite.
- Read the AGENTS.md for the 30-line project overview.
- Read `framework/README.md` for the renderer pipeline.
- Read `docs/BUILD.md` for the build system.
- Read `docs/USE.md` for the teacher workflow.
